# M1 — Environment: store, policy, tools, policy engine

## What we built
- SQLite schema (`env/schema.py`), deterministic Faker seed (50 customers, 200 orders), frozen clock (`env/store.py`).
- Fixture patches with relative times (`delivered_hours_ago: 20`) and `fresh_env(patch)` (copy of a seeded template).
- The written policy (`docs/policy/ShopSetu_Support_Policy.md`, rule IDs ID-1…TONE-1 + worked examples).
- 12 tools with Pydantic inputs whose docstrings are the model-facing descriptions (`tools/`).
- The deterministic policy engine (`policy_engine.py`) + 37 tests incl. Hypothesis properties.

**Why this design.** The model is untrusted (it can misread policy or be injected), so the rules that protect money and
identity are code. Tools return errors as data so the model can recover (e.g. ask for verification) instead of the
run crashing. Alternative: let the prompt carry the policy only — that is exactly D0/D1, and the eval measures the gap.

## Key concepts
- **Errors as data**: `tools/base.py::err` → `{"ok": false, "error_code", "message", "hint", "rule_ids"}`. The hint
  tells the model the next step.
- **Engine shape**: `evaluate(action, params, env, session) -> Decision(allow|deny|needs_approval, rule_ids, message)`.
  It never writes. Read `check_refund` top to bottom: identity → REF-5 → REF-3 → REF-1/REF-2 → FR-1 → REF-4.
- **`refundable_amount`** encodes REF-3: returned items (+ shipping under RET-4 or a full return), minus prior refunds.
- **Idempotency**: `tools/registry.py::execute_tool` stores each successful write under its key and replays it; domain
  rows also carry the key UNIQUE, which covers a crash between the two writes.
- **Frozen clock**: `Env.now` from the `meta` table; windows like "48 hours" are reproducible on any day.
- **Property tests**: `test_property_refunds_never_exceed_paid_and_never_to_unverified_upi` throws random refund
  sequences (even human-approved ones) at the tools and checks the invariants on the final DB.

## Interview questions
1. **Why a deterministic policy engine if the model already knows the policy?** Because "knows" is probabilistic and
   attackable. The engine makes invariant-violating actions impossible regardless of model output: a refund to an
   unverified UPI ID is refused by code. The prompt still matters for utility (choosing the right action), but safety
   doesn't depend on it.
2. **What does a Hypothesis property test give you that example tests don't?** Example tests check cases I thought
   of; Hypothesis generates many sequences (amounts, destinations, customers, approval flags) and shrinks any failure
   to a minimal counterexample. It checks an invariant ("sum of refunds ≤ paid") rather than a case.
3. **Why are idempotency keys derived from the tool-use ID?** Retries after a crash replay the same tool-use ID, so the
   same key; two genuinely different calls have different IDs. A model-chosen key could be reused by mistake and
   silently swallow a legitimate second action.

## Break-it exercise
In `policy_engine.py::refundable_amount`, delete `- already` from the return value (so prior refunds aren't
subtracted). Run `uv run pytest tests/unit/test_policy_engine.py`. Expected: the Hypothesis property fails with a
shrunk example of two refunds on one order whose sum exceeds the total. That shrunk example is your diagnosis.
