# M4 — Human approval

## What we built
- Risk tiers (`hitl/approvals.py::tier`): reads 0, allowed writes 1, `needs_approval` writes 2.
- At D3 the `tools` node dry-runs writes (`tools/write.py::preview`); tier-2 → approval row + `approval_gate`.
- `approval_gate` uses `interrupt(request, response_schema=ApprovalResponse)` and resumes with `Command(resume=…)`.
- `trustdesk approvals list|approve|reject`, `GET/POST /approvals`, and the web queue.
- Audit log rows for agent decisions and human decisions (with trace ID).

**Why this design.** The engine is the single source of "what needs a human" (REF-4, GW-1 over limit, FR-1), so tiers
can't drift from policy. Deny decisions never reach a human: even a rubber-stamp approver can't approve a refund to
an attacker's UPI. Alternative: interrupt before every write — too noisy; humans would rubber-stamp.

## Key concepts
- **Resume re-runs the node**: everything above `interrupt()` must be pure. The approval row is created in the
  *tools* node (idempotent on `tool_use_id`) so the gate itself has no side effects before the interrupt.
- **Exactly-once after approval**: the write uses key `session:tool_use_id`; `record_decision` only updates rows still
  `pending`. A crash after the write and before the checkpoint replays harmlessly.
- **Durability**: `SqliteSaver` stores the paused run; `test_pending_approval_survives_restart` closes the DB
  connection, builds a new graph, and resumes.
- **Approved ≠ unchecked**: `approved_by` only turns `needs_approval` into allow; deny rules still apply.

## Interview questions
1. **What's the subtle bug people hit with LangGraph interrupts?** Side effects before `interrupt()` run twice,
   because the node restarts from the top on resume. We keep the gate pure up to the interrupt, do the write after
   it, and protect the write with an idempotency key.
2. **Why does the policy engine still matter if a human approves?** Defense in depth: humans get tired and approve
   everything. Only `needs_approval` outcomes can be approved; `deny` (wrong destination, over the cap, wrong account)
   is never offered to a human. The rubber-stamp eval mode measures this.
3. **What does the approver see, and why?** The action and parameters, the engine's rule IDs, the agent's own
   justification text, and the last conversation turns. That's enough to decide without reading the whole transcript
   and makes the agent's reasoning auditable.

## Break-it exercise
In `graph.py::approval_gate`, move `approvals.record_decision(...)` *above* the `interrupt(...)` line (pass a dummy
"approve"). Run `uv run pytest tests/integration/test_graph.py -k reject`. Expected: the test fails — the request is
already marked approved before the human answered, and the audit log has a human decision the human never made.
