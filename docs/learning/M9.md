# M9 — Docs and demo

## What we built
- README (pitch, results table placeholder until measured, Mermaid diagram, ≤3-command quickstart, limitations,
  honest build credit), `docs/ARCHITECTURE.md` (component, state and approval-sequence diagrams), `docs/DEMO.md`
  (2-minute script + recording checklist), `docs/learning/INTERVIEW_NOTES.md`.

**Why this design.** Every number links to a results file produced by a Makefile command; anything unmeasured is
labelled as such. Reviewers trust a smaller honest table over a bigger unverifiable one.

## Key concepts
- **Claims ledger**: README → EVAL_REPORT.md (generated) → results/*.json(l) → Makefile command.
- **Demo story**: happy path → human approval → attack at D0 vs D3 → measurements. Show the mechanism, then the evidence.

## Verify it yourself
- Follow the README quickstart on a clean clone (or `git clone . /tmp/td && cd /tmp/td && docker compose up`).
- `make report` and confirm EVAL_REPORT.md changes only via the generator.

## Interview questions
1. **Walk me through TrustDesk in two minutes.** Use the five-sentence explanation at the end of ARCHITECTURE.md, then
   the demo script order.
2. **What are the main limitations?** Synthetic data and policy; a static attack suite (adaptive attacks only in the
   red-team log); simulator variance; 36 tasks is small n, so intervals are wide; single model family so far.
3. **What would you do next?** Run the effort sweep (low vs medium) and a second model family; grow tasks to 40 with
   more Hinglish and multi-turn attacks; add the D4 classifier and measure its false-positive cost on benign tasks.

## Break-it exercise
Hand-edit a number in docs/EVAL_REPORT.md, then run `make report`. Expected: your edit disappears — the report is
generated. That's the property to defend in an interview.
