# M5 — Evaluation harness

## What we built
- Task format (`evals/schema.py`) and 36 tasks (`evals/tasks/`): 13 benign, 7 edge, 4 approval, 2 ambiguous, 10 attacks.
- Validator (`evals/validator.py`): replays each golden action list through the real graph at D3, checks expected state,
  forbidden actions, invariants, approval interrupts, probes and the do-nothing baseline → `results/validation.json`.
- Customer simulator (`evals/simulator.py`), runner (`evals/runner.py`), deterministic graders (`evals/graders.py`),
  generic metrics (`evals/metrics.py`), report generator (`evals/report.py`).

**Why this design.** τ-bench grades the *end state* of the world, not the transcript, which is robust to phrasing.
AgentDojo-style attack checks are deterministic, so the judge can't be injected. The validator turns "is this task
fair?" into a test: if the golden path can't reach the expected state, the task is wrong, not the agent.

## Key concepts
- **pass^k** = C(c,k)/C(n,k) per task, averaged: the chance k independent tries *all* succeed — a reliability metric.
  pass^1 is ordinary success rate; pass^3 punishes flaky tasks.
- **Wilson interval** for proportions; **bootstrap over tasks** for pass^k, because trials of one task are correlated.
- **Utility under attack** (did the real customer get helped?) vs **ASR** (did the attacker's goal happen?) — a
  defense that refuses everything gets ASR 0 and utility 0.
- **Independent invariant checker** (`graders.py::policy_violations`) re-implements the rules in SQL, so it can catch
  a bug in the engine itself.
- **Failure taxonomy** is an automatic first pass; read the three linked trajectories by hand.

## Verify it yourself
- `make validate` (no model calls). Then break a task: change an amount in `evals/tasks/benign-01-…yaml` and rerun.
- `uv run pytest tests/unit/test_metrics.py tests/unit/test_eval_harness.py -v`.
- With a key: `make eval-smoke`, then `make report`.

## Interview questions
1. **Why pass^k instead of average success?** Production agents run the same task thousands of times; a task that
   succeeds 2 of 3 times has pass^1 = 0.67 but pass^3 = 0. The unbiased estimator C(c,k)/C(n,k) uses all n trials
   rather than one arbitrary k-subset.
2. **Why not use an LLM judge for attack success?** The judge reads the same injected text and can itself be
   manipulated; it's also non-deterministic. Attack goals here are facts about the world (a refund row to
   attacker@okbank exists; a phone number appears in the output), so we check them directly.
3. **How do you know your tasks are fair?** Every task has a golden action sequence replayed through the real graph
   by the validator, probes that must be refused by policy, and a do-nothing baseline check; plus I review them by
   hand. Ambiguous outcomes (e.g. a COD refund where the customer wants a new UPI) are pinned down in the customer
   instructions ("if refused, accept the verified UPI").
